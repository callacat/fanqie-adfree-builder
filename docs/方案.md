## 1. 工具链
- apktool ≥2.9（先 `d -r` 只解码 dex 试水；资源重建报错再用 `--use-aapt1` 或干脆 `-r` 路线：不解资源，直接改 dex 后用 zip 重入方式回填 classes*.dex —— 字节系 ARSC 混淆是已知雷区，**优先考虑不动 resources.arsc 的路线**）。
- 签名：`zipalign -P 16`（so 未压缩对齐）→ `apksigner sign --v1-enabled --v2-enabled --v3-enabled`（minSdk 26+ 用 v2+v3 为主）→ `apksigner verify`。
- keytool 自签一把调试 keystore 即可。

工程注意：
- 方法签名以 **73532 实际 smali 为准**（v0.4.0 记录的行号/参数是 LSPosed 运行时视角，静态 smali 找同名方法+同参数即可；找不到就 grep 该类名列出全部方法人工判定，**逐一记录 find/未find 清单**）。
- return false 的 smali 写法：`const/4 v0, 0x0` + `return v0`（boolean），void 用 `return-void`；注意寄存器数 `.registers/.locals` 调整。
- 混淆类（如 h83.a）按接口名/字符串常量反查，别硬编码猜。

## 3. 签名校验应对（分级）
- L1（先做）：静态 grep `getPackageInfo|GET_SIGNATURES|GET_SIGNING_CERTIFICATES|SigningInfo|toCharsString|MessageDigest` 定位 Java 层自检；**只记录清单不先改**。
- L2：装上后启动闪退/弹异常 → 按清单 patch 对应 boolean/比较逻辑为「恒通过」。
- L3：仍闪退且堆栈指向 native → 重点嫌疑 `libmetasec_ml.so`/`liblynxsecurity.so`；先 patch Java 调用点（不走 so），真不行再评估 so 层（成本高，先报告再动）。
- 记录每次改动的 smali diff（git init smali 目录，天然 diff）。

## 4. 风险与备案
- v7a-only 包跑 x86_64 模拟器靠 native bridge：性能打折/个别 so 可能崩——实测说话；若 native bridge 跑不动，备案 = 找 6.x 时代包（老 HookFanqie 资料最多）或改用 arm64 真机路线（东哥 OPPO）。
- checkAdAvailable 全 false 的副作用（初始化依赖）：按 §2.8 备案收窄。
- 73532 换签后 App 自检是否拒绝启动 = 公开资料无定论（存疑项），实测为准。

## 5. 分工与流程
1. 码农：apktool decode → smali patch（§2 清单）→ build → zipalign → sign → **自测安装+启动 logcat** → 交付 APK 到本目录 + 修改点报告（`码农报告.md`）。
